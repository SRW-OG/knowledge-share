# 安全运营 Agent 落地：让 LLM 亲手把自己「炼」成规则

## 一、问题现状：安全运营的痛点与 LLM 引入背景

### 背景描述

安全运营面临的核心挑战是**告警类型千变万化，人工写规则永远追不上新模式**。当新型攻击出现时，安全团队往往需要手动分析大量告警样本，提取共性特征，再转化为规则。这一过程耗时耗力，且难以覆盖所有场景。

### 风险评估

- **人工规则编写效率低**：新告警类型出现时，需要安全分析师花费数小时甚至数天分析
- **规则覆盖不足**：传统规则引擎只能处理已知模式，未知威胁依赖人工研判
- **运营成本高**：随着业务扩张，告警量指数增长，人工处理不可持续

### 影响范围

- 安全运营团队（SecOps）
- 告警研判系统
- SIEM/SOAR 平台

## 二、解决思路与方案对比

### 三种阶段的对比分析

| 阶段 | LLM 角色 | 人的角色 | 一句话描述 | 可控性 |
|------|----------|----------|------------|--------|
| **代笔期** | 写代码的工具 | 提需求、审代码 | LLM 帮你写代码，你说它写 | ✅ 高 |
| **共生期** | 被代码调用的能力 | 设计流程、定标准 | LLM 嵌入系统，代码和模型互相配合 | ✅ 高 |
| **自主期** | 主动发现问题的 Agent | 设目标、审结果 | Agent 自己发现问题、解决问题 | ❌ 低 |

### 方案选择

**推荐方案：共生期（代码调用 LLM）**

理由：
1. **产出稳定**：LLM 输出受代码校验机制约束
2. **质量可量化**：覆盖率、误报率等确定性指标可评估
3. **可控性强**：执行路径由状态机控制，LLM 只在特定节点被调用

## 三、最佳实践框架

### rule_iterate 模块设计

核心是一个手写的 **ReAct 模式状态机**——执行路径由代码严格控制，LLM 只在以下两个节点被调用：
1. **生成规则**：分析告警样本，提取共性特征
2. **反思原因**：分析覆盖率不足的原因，调整规则

### 核心流程

```
输入: 待覆盖的告警样本(goodcase) + 不能误伤的样本(badcase)
   ↓
Step 1: LLM 分析告警共性，生成候选规则
   ↓
Step 2: 代码验证覆盖率（必须 100%）
   ↓
Step 3: 未覆盖？LLM 反思原因，生成补充规则
   ↓
Step 4: 验证误报率（必须 0%）
   ↓
循环...直到满足指标
   ↓
输出: 可直接使用的 YAML 规则文件
```

### 关键原则

- **LLM 负责「想」，代码负责「验」**
- 规则好不好，不靠 LLM 自己说，靠代码在真实数据上跑一遍来判断
- 迭代该不该继续，不靠 LLM 决定，靠覆盖率指标说话

## 四、具体操作步骤

### 步骤 1：构建告警样本库

```python
# 准备样本数据
goodcases = [...]  # 需要覆盖的告警样本
badcases = [...]   # 不能误伤的其他告警样本
```

### 步骤 2：实现 rule_iterate 状态机

```python
class RuleIterate:
    def __init__(self, llm_client):
        self.llm = llm_client
        self.max_iterations = 10
    
    def generate_rule(self, goodcases):
        prompt = f"分析以下{len(goodcases)}条告警的共性，生成一条候选规则..."
        return self.llm.chat(prompt)
    
    def verify_coverage(self, rule, goodcases):
        # 代码验证覆盖率
        covered = [c for c in goodcases if rule.matches(c)]
        return len(covered) / len(goodcases)
    
    def verify_false_positive(self, rule, badcases):
        # 代码验证误报率
        matched = [c for c in badcases if rule.matches(c)]
        return len(matched) == 0
    
    def iterate(self, goodcases, badcases):
        for i in range(self.max_iterations):
            rule = self.generate_rule(goodcases)
            coverage = self.verify_coverage(rule, goodcases)
            fp_rate = self.verify_false_positive(rule, badcases)
            
            if coverage == 1.0 and fp_rate == 0:
                return rule  # 成功
            
            # 反馈给 LLM 改进
            feedback = f"覆盖率 {coverage*100}%，误报 {fp_rate*100}%"
            self.llm.reflect(feedback)
        
        return None  # 达到最大迭代次数
```

### 步骤 3：与规则引擎集成

```python
# 生成的规则写入 YAML
def save_rule(rule, output_path):
    with open(output_path, 'w') as f:
        yaml.dump(rule, f)

# 规则引擎加载
def load_rules(rule_file):
    with open(rule_file) as f:
        return yaml.safe_load(f)
```

### 步骤 4：验证与部署

```bash
# 测试规则覆盖率
python test_coverage.py --rule rules/generated.yaml

# 部署到生产环境
kubectl apply -f rules/generated.yaml
```

## 五、总结与建议

### 核心经验

1. **确定性校验才是锚**
   - 能否用代码校验 LLM 产出，是决定能否落地的关键
   - 有硬性指标（覆盖率 100%、误报率 0%），LLM 再发散也被拉回来
   - 没有硬性校验标准，Agent 的发散就没有锚点

2. **能用代码管住的事，别指望 Prompt**
   - 代码约束：状态机控制执行路径、覆盖率决定是否继续、最大迭代次数
   - Prompt 约束：自然语言级别的"拜托"，LLM 可随时"变通绕过"
   - **硬约束必须交给代码，Prompt 只做软引导**

3. **好的 Agent 会让自己变得不再被需要**
   - Agent 的成功标志：让分析的 case 越来越少
   - 每成功分析一类场景 → 固化为确定性规则 → 下次不再需要 Agent
   - 这是"从不确定到确定"的过程

### 成效回顾

| 阶段 | 规则覆盖率 | Agent 介入需求 |
|------|------------|----------------|
| 项目初期 | 0% | 每条告警都需要 |
| 引入规则引擎后 | 60% | 大幅减少 |
| rule_iterate 持续运行后 | 80%+ | 持续降低 |

### 后续建议

1. **渐进放权**：Agent 建议人执行 → Agent 执行人抽检 → Agent 执行 Agent 校验
2. **每步都要有兜底**：每一步放权都必须有确定性校验机制
3. **让 Agent 做「规则生产者」，而不是「分析师」**
