# 0元购漏洞：餐厅预订系统价格篡改攻击

## 1. 问题现状 (Current Status & Problem Analysis)

### 背景描述

"0元购"漏洞是电商/O2O系统中极为常见的价格篡改型逻辑漏洞。攻击者通过拦截并修改支付数据包中的价格参数，使服务端认为原价商品为极低价格，从而以几乎为零的代价获取商品或服务。

**本文案例**：某餐厅预订系统——用户登录后可选择套餐预订，支付金额在数据包中以明文形式传输且未做服务端校验。

### 风险评估

| 风险类型 | 描述 | 严重程度 |
|----------|------|----------|
| 订单篡改 | 修改订单金额进行支付 | 高 |
| 业务逻辑缺陷 | 客户端校验可被轻易绕过 | 高 |
| 财产损失 | 攻击者可零成本获取高价值套餐 | 高 |

### 影响范围

- 所有在支付数据包中明文传输价格且服务端未校验的系统
- 典型O2O平台（餐饮、票务、电商）订单模块
- 未对用户角色权限和订单状态做严格校验的后台管理系统

## 2. 解决思路与方案对比 (Solution Options & Analysis)

### 核心问题定位

**漏洞根因**：服务端过度信任客户端传来的价格数据，未在服务端重新计算并校验订单金额。

### 攻击路径对比

| 路径 | 描述 | 难度 | 风险 |
|------|------|------|------|
| 硬撞登录口 | 直接爆破后台登录接口 | 低→高 | 易触发风控/封禁 |
| 注册进后台 | 先注册账号，再挖掘已注册用户功能点 | 低 | 隐蔽性高 |
| 抓包篡改价格 | 拦截支付数据包修改金额参数 | 低 | 需一定工具使用经验 |

### 防御方案对比

| 方案 | 实现难度 | 防御效果 | 适用场景 |
|------|----------|----------|----------|
| 服务端价格校验 | 中 | ★★★★★ | 所有交易系统 |
| 签名/加密传输 | 高 | ★★★★☆ | 高安全需求 |
| 订单金额哈希风控 | 低 | ★★★☆☆ | 快速止血 |

## 3. 最佳实践框架 (Best Practice Framework)

### 推荐方案：服务端价格强制校验

**核心原则**：服务端必须根据商品ID从数据库重新计算价格，绝不信任客户端传来的价格字段。

### 安全架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                      客户端                                 │
├─────────────────────────────────────────────────────────────┤
│  选择商品 → 发起订单请求（不含价格）→ 发起支付 → 完成交易      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                      服务端                                  │
├─────────────────────────────────────────────────────────────┤
│  接收订单请求 → 查询商品定价 → 生成订单（含服务端计算价格）    │
│  接收支付请求 → 验证订单金额与支付金额是否匹配 → 执行交易      │
└─────────────────────────────────────────────────────────────┘
```

### 关键风控点

| 风控节点 | 实现要求 |
|----------|----------|
| 价格来源 | 只能从服务端数据库/配置获取，禁止客户端传递 |
| 订单生成 | 服务端独立生成订单号和金额，不依赖客户端数据 |
| 支付校验 | 支付时比对：支付金额 == 订单金额 |
| 越权检查 | 订单与用户ID绑定校验，防止替他人下单 |
| 频率限制 | 同一用户短时间订单数量限制 |

## 5. 总结与建议 (Summary & Recommendations)

### 漏洞成因总结

| 原因 | 说明 |
|------|------|
| 客户端校验 | 仅前端JS校验，无服务端价格校验 |
| 明文传输 | 金额以明文在请求体中传输 |
| 缺乏签名 | 请求参数无完整性保护，可随意修改 |

### 修复建议

1. **服务端强制验价**：订单金额必须从服务端商品定价表重新计算
2. **请求签名机制**：对订单参数添加签名，服务端验签通过后才处理
3. **金额一致性校验**：支付金额必须与订单金额完全匹配
4. **日志审计**：对订单金额异常低的情况记录审计日志

### 挖洞思路总结

| 技巧 | 适用场景 |
|------|----------|
| 注册进后台 > 硬撞登录口 | 绕过登录暴力破解的高调风险 |
| 寻找"最低起购"功能点 | 绕过前端份数限制校验 |
| 抓包拦截第二数据包 | 第一个包多为鉴权，第二个才是支付 |
